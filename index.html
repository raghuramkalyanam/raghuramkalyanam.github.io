Internal Staff Assistant

A leading Swiss collection agency employs internal and external call-centre staff to answer public enquiries about the national broadcasting fee, drawing on official work-instruction manuals scattered across a wiki, PDFs and internal sites. The challenge was locating the right passage quickly, across three languages.

I built the assistant that answers those questions, grounding every response strictly in the manuals and replying in German, French or Italian. It also displays the manual's own screenshots alongside each answer, as staff had requested.

Responsibilities

  • Corrected how the assistant identifies the key term in a German question: compound words were being mishandled, which often led to the wrong manual being selected.
  • Designed a way to present the manuals' screenshots without an image-reading model: the assistant selects a section rather than an image, and the screenshots for that section are attached automatically in their original order.
  • Rebuilt the measurement harness to test the application's own code rather than a simplified stand-in, and introduced an independent model to grade answer quality, so the assistant does not evaluate its own output.
  • Introduced a reviewer panel within the product so staff could rate the reference questions and answers, and acted on the results: several weak questions were withdrawn, weak reference answers were rewritten, and a complaint that a manual had "not been consulted" was traced to two search thresholds.
  • Made index rebuilds atomic, added company login with administrator rights derived from directory group membership, and built an administration panel for re-importing documents and rebuilding the index.
  • Audited the deployment and fixed two defects it revealed: every release was deleting chat history and user feedback, and the search database was unencrypted on the network.
  • Mapped the safeguards required by the system's data-protection impact assessment, together with the OWASP Top 10 risks for AI applications, onto specific implemented controls.

Retrieval architecture redesign

The retrieval path was redesigned: the original version had the assistant itself browse the manual catalogue in two passes before it could start answering, which made every response noticeably slower and more expensive. Replacing that browsing step with a dedicated search engine cut both the wait and the cost by a large margin. Separately, a fix to how German compound words are handled in the assistant's search term made it noticeably more reliable at finding the right manual.

Retrieval: lexical, deliberately

The system uses no embeddings and no vector store — an explicit architecture decision recorded in an ADR. The corpus is small, curated, structured by numbered chapters, and German-dominant, so OpenSearch's per-language analysers can handle stemming, stop words and umlaut folding. This gives accurate retrieval with no embedding infrastructure to operate and a fully debuggable ranking. The escalation path to a vector database is documented rather than left unaddressed.

Query matching combines several tuned signals in a documented order: searching across section titles and body text in all three languages, weighting toward a manual whose title matches the topic directly even when its own sections are titled generically (e.g. "Step-by-step guide"), and boosting the query's main noun with German-aware handling of compound words — a single fix here raised the hit rate from 0.70 to 0.95. Sections also carry LLM-generated topic tags that provide a modest additional boost, tuned low enough that a stray tag can never outrank the right manual, and nine common boilerplate headings are demoted rather than excluded outright.

Trimming is three composable stages with distinct jobs, because raw lexical scores are not comparable across questions: absolute floor (refusal + per-hit filter), relative knee (cut at the first ≥40% consecutive score drop), and content dedup at 0.95 similarity. Plus version-aware dedup and year-family collapse — manuals differing only by year collapse to the newest unless the question names a year, applied to the full deduped set before capping, since capping first would drop rows the collapse would have promoted.

Vision-free multimodal retrieval

During ingestion, every image-bearing section is catalogued with its position and an LLM-generated German summary, covering all 2,098 images across 498 sections. At answer time, a smaller model selects which sections are relevant from these summaries alone, and only images belonging to a selected section are shown, in their original order. Screenshots are shown for how-to questions and left out for purely factual ones, where they would just be noise. Because the answer streams in gradually, image references are handled carefully so a partial reference is never shown mid-stream: the real screenshot and its caption only appear once the reference is fully resolved, and only for images that were legitimately cited.

Answer validation critic

Every answer passes through five checks, ordered from cheapest to most expensive: language, verbosity, self-refusal, a lightweight groundedness check that catches most cases without needing a model call, and finally a full groundedness and relevance review by a judge model. Depending on the outcome, the assistant may retry with a correction, or salvage a mostly-good answer by removing only the unsupported sentences and flagging the removal, rather than discarding the whole response. Fabricated citations are also detected and removed. If no relevant content is found at all, the assistant returns a fixed refusal without calling the answer model, which avoids a 20–40 second wait and rules out hallucination on empty input entirely.

Evaluation harness

The evaluation harness runs the application's actual retrieval code directly, rather than a reimplemented stand-in, so its numbers reflect what production actually does — a true retrieval hit rate of roughly 81%. Metrics cover answer faithfulness and relevance, judged by a separate model with a version-pinned prompt so results stay comparable over time, plus retrieval-specific measures that separate a retrieval miss from a generation failure, so a drop in quality can be traced to the right stage. Results are logged per question as well as in aggregate, so a regression can be traced to the exact question responsible.

Golden-set lifecycle and feedback loop

The reference question-answer pairs used for evaluation were built up over several review rounds, span a wide range of source manuals, and are translated into French and Italian. Candidate pairs are generated by an LLM but never overwrite an already-reviewed set, and a dedicated review tool lets a person accept, edit or reject each one, improve reference answers, and test parameter changes against the set. Inside the product itself, staff can vote on individual answers; a repeat vote updates rather than duplicates, and each vote is tagged with the model version in use, so quality can be tracked across model changes. Votes on translated answers are tracked separately from the German original, since a downvote there might reflect the translation rather than the underlying answer. This internal review signal is kept entirely separate from end-user thumbs-up/down feedback.

Zero-downtime reindexing and reingestion

The application always queries through an alias rather than a specific index, so rebuilding the search index never causes downtime. A rebuild fills a new index, marks it complete, atomically switches the alias over, and then removes old indices while keeping one as a rollback option. This handles several edge cases cleanly: a half-built index from an interrupted rebuild is cleaned up before it could accidentally become the rollback target, and the very first deployment transitions smoothly from a plain index into this alias-based setup. The same approach covers a full reingestion when source manuals are updated: document conversion, chunking and image cataloguing all run again into a fresh index in the background, with the alias switch as the only visible change once it's ready.

Performance monitoring

A repetition penalty is applied consistently across both the retrieval and answer calls to prevent runaway generation loops. Deployments are monitored to catch containers silently serving stale configuration. Throughput reporting accounts for time to first token rather than decode speed alone, giving an accurate view of real-world latency (roughly 17 tok/s effective). Input token usage has a structural floor of roughly 9,000–10,000 tokens from an early catalogue step, separate from the answer-generation step that the tuning options actually affect.

Deterministic, cacheable prompt design

The full rule set is compressed directly into a stable system prompt rather than retrieved from a knowledge base on each request, which keeps every run consistent and makes the prompt cacheable. This keeps the prompt a small fraction of the size of a retrieval-based equivalent, measured directly.

Design alternatives considered

An alternative two-step design has the model call a tool to fetch relevant rules before drafting. It reaches somewhat higher correctness but roughly doubles typical latency, with occasional outliers running far longer still, and depends on tool-call reliability — trade-offs documented alongside the chosen design.

Evaluation architecture

Two complementary layers, both driving the model through the real chat interface so the actual system prompt, permissions and attachments are exercised, not a simplified stand-in:

  • Deterministic layer — a rule-based checker that verifies mechanically checkable instructions directly: required and forbidden phrasing, sentence-length limits, formatting rules, output language, and resistance to prompt injection or system-prompt leaks. This follows the principle that anything checkable by code should be checked by code rather than judged by a model, which also removed a class of false positives caused by comparing a corrected text against its own trailing change summary.
  • Judge layer — a separate model, from a different provider than the assistant itself, scores responses against explicit criteria drawn from the test cases, which avoids the leniency a model can show toward outputs from its own family. Both layers score a single response and can run independently, so a full run has a fast, free path and a slower, paid path.

The suite also covers multi-turn conversations that include file uploads, distinguishing genuine document content from empty uploads so the assistant isn't penalised for correctly declining to answer from nothing. Score reporting was adjusted so deterministic results always appear even when both layers run together, and the evaluation suite is kept isolated from the rest of the tooling to avoid dependency conflicts.

Sovereignty and access controls

Document embedding is disabled everywhere: uploaded files are extracted and passed to the model as plain source text, which keeps the embedding step entirely out of the confidential-data path. A custom German citation template only allows a reference marker when a source carries an explicit id, guarding against hallucinated citations. Each assistant is issued its own gateway key with a restricted model allowlist, and that key also identifies it in the metrics system, which is what makes per-assistant cost attribution possible. New accounts have no access until explicitly approved, admin chat access and data export are disabled, chat sharing and public links are off, and telemetry is switched off for the air-gapped environment.

Prompt engineering as a versioned artefact

The German system prompt runs to several dozen lines, with a pre-flight block of absolute rules, a multi-point self-check before sending, and explicit precedence when rules conflict (plain-language requirements override general style rules). Documented exceptions include: legal role terms must not be neutralised, gender-inherent nouns are preserved, already-correct pair forms are left alone, verbatim quotes are protected at every nesting level, and table cells are exempt from prose formatting rules. The prompt also fills in its own backing model's name automatically at startup, so the assistant can accurately state which model is answering.
